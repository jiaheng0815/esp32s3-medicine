# ESP32-S3-CAM (OV3660) + ST7735S 用药助手

一块 ESP32-S3 + 摄像头 + 小屏 + 麦克风 + 喇叭，做成**会说话的用药提醒器**：

| 能力 | 说明 |
|---|---|
| **实时取景** | OV3660 的画面直接怼到 128x160 的 ST7735S 屏上，不压缩、不连电脑，约 17FPS |
| **拍照识药** | 短按 BOOT 拍一张丢给智谱 GLM-4.6V 认药名，再**本地**算出"现在该不该吃" |
| **语音交互** | 按住 BOOT 说话（「阿莫西林吃了」），松手后自动识别 → 本地判断 → 喇叭读出来 |
| **用药记忆** | 吃了什么、一天几次，存在设备本地 NVS 里，断网也能查 |
| **网页** | 手机打开设备 IP，看记录、手动增删、打字代替说话 |

设计目标是**给不方便看手机的人用**：结果同时上屏、出声、还能在网页上回看。
只有三件事需要联网调模型 —— 图片认药名、语音转文字、文字转语音；**该不该吃这个判断
永远在本地算**，快、免费，而且时间算术交给代码比交给模型可靠得多。

接线见 [接线图.md](接线图.md)。

## 怎么用

### 1. 接线

见 [接线图.md](接线图.md)。有三块东西要接：

| 模块 | 线数 | 说明 |
|---|---|---|
| ST7735S 屏 | 6 根 | 最基础，不接就什么都看不到 |
| INMP441 麦克风 | 6 根 | 语音输入。**L/R 必须接 GND**，悬空则读数乱跳 |
| MAX98357A 功放 + 喇叭 | 7 根 | 语音播报。**SD 要接 GPIO38**，不能直接接 3V3（原因见接线图）|

摄像头是板上排线，不用管。

> **只想先跑通拍照识别**的话，麦克风和功放可以先不接 —— 语音只在按住 BOOT 时才用到，
> 其他功能照常工作。网页上的文本框就是给这种情况兜底的。

### 2. 填 API Key

打开 `src/secrets.h`，把 `ZHIPU_API_KEY` 换成你自己的：

```c
#define ZHIPU_API_KEY "你的key"
```

去 https://open.bigmodel.cn 注册后创建密钥。这**一个 key 同时用于三件事**：

| 用途 | 模型 | 费用 |
|---|---|---|
| 拍照认药名 | `glm-4.6v-flash` | **免费** |
| 拍照认药名 | `glm-4.6v` | 输入 **1 元/百万 tokens**；输出 **3 元/百万 tokens** |
| 语音转文字 | `glm-asr-2512` | 0.06 元/分钟 |
| 文字转语音 | `glm-tts` | 2 元/万字符（一条 30 字的提醒约 0.006 元） |

> 说明：`glm-4.6v-flash` 免费；`glm-4.6v` 为付费基础版。`glm-tts` 按字符计费。
**只拍照不用充值。** 要用语音的话充几块钱就够用很久 —— 按一天说 20 次、每次 5 秒算，
一个月大约 0.3 元。

这个文件被 `.gitignore` 忽略，不会进版本库。

### 3. 编译烧录

```bash
pio run -t upload
pio device monitor
```

> `pio` 提示「不是内部或外部命令」的话，用完整路径：
> `~/.platformio/penv/Scripts/pio.exe run -t upload -d "项目目录"`

### 4. 先验硬件（接了麦克风/功放就必须做）

**别跳过。** INMP441 + ESP32-S3 这个组合有个已知案例：读数恒为 0，换过 3 个麦克风、
2 块开发板都没解决。等它接进主流程再出问题的话，你分不清是接线还是代码。

固件里内置了**两级**自检，从最基础的开始。

#### 第一级：`HW_TEST`

把 `src/main.cpp` 顶部的 `HW_TEST` 改成 `1` 再烧录（平时是 `0`），**不连 WiFi**，屏幕依次做三件事：

| 步骤 | 你会看到 / 听到 | 通过标准 |
|---|---|---|
| ① 屏幕 | 闪 红→绿→蓝→白，然后画一段中英文 | 都看得到 = 屏幕 + 中文字库都通 |
| ② 功放 | 一声 1kHz 的"嘀" | 听得到 = 功放 + 喇叭通 |
| ③ 麦克风 | 屏幕中间一条中线，下面电平条 | **对着麦说话，波形跟着动** = 麦克风通 |

第 ③ 步是重点 —— **波形直接画在屏幕上**，不用按键、不用连串口，说话就有反应：

```
┌────────────────────────────┐
│ MIC TEST   peak  6218      │ ← 峰值，说话时明显变大
├────────────────────────────┤
│         ╱╲    ╱╲           │
│ ───────╱──╲──╱──╲────────  │ ← 说话时波形这样起伏
│       ╲╱    ╲╱             │   (中线 = 静音时的位置)
├────────────────────────────┤
│ ████████░░░░░░░░░░         │ ← 电平条
└────────────────────────────┘
  no key needed - just talk
```

**波形是平的就说明有问题**，按现象查：

| 现象 | 查哪里 |
|---|---|
| 波形贴着中线不动，峰值一直是 0 | **麦克风没通**：L/R 是否接 GND、VDD 是否 3V3、SD 是否在 GPIO40 |
| 波形一直在抖，但说话时不变大 | SD 接错脚，或者麦克风本身是坏的 |
| 波形随说话明显起伏 | ✅ 麦克风通过 |

#### 第二级：`MIC_SELFTEST` —— 完整音频链路

第一级通过后，把 `HW_TEST` 改成 `0`、`src/voice.h` 的 `MIC_SELFTEST` 改成 `1` 重新烧录。

这一级**也不连 WiFi**，开机后：

- **放一声 1kHz 的"嘀"** → 听到 = 功放侧通了。
  没听到就查：VIN 是不是 5V、SD(GPIO38) 有没有接到模块的 SD/EN、
  SPK± 是不是接在喇叭两端（**都不能接 GND**）
- **按住 BOOT 说话** → 串口打 ASCII 波形，松手后喇叭**回放**。
  有波形 + 能听到自己 = 麦克风侧通了

回放这一步额外能验证**采样率配置**：如果回放出来音调明显低沉、时长翻倍，
就是采样率配错了。

**波形和回放要分开看**，这是这一步的全部意义：

| 现象 | 结论 |
|---|---|
| 波形是直线，串口提示"整段几乎没信号" | **麦克风侧**。查 L/R 是否接 GND、VDD 是否 3V3、SD 是否在 GPIO40 |
| 有波形，但回放没声音 | **功放侧**。查 VIN / SD 使能 / 喇叭接线 |
| 波形正常，回放能听到自己 | ✅ 整条音频链路通了 |

串口输出长这样（对着麦克风说话时）：

```
[自检] 录到 64000 字节 (2.0 秒), 峰值 8231, 范围 [-9012, 8231], 非零 31987/32000
    [ .:-=+*#%@@%#*+=-:..  .:=+*#%@@#*+=:.  ..::-=+*#*+=-:.  .:-=+*#%@@#*+= ]
[自检] 回放:
```

#### 全验完之后

三个开关都归 0，重新烧录进正常模式：

| 开关 | 位置 | 改成 |
|---|---|---|
| `HW_TEST` | `main.cpp` | `0` |
| `MIC_SELFTEST` | `voice.h` | `0` |
| `IS_TEST` | `main.cpp` | `0`（**必须是 0**）|

> ⚠️ **`IS_TEST` 是 `1` 的话等于白干** —— 它会退回「纯识图」模式，把语音、用药记忆、
> 网页全关掉（拍照还能用，但不认药名、不播报）。

> **帧率没了？** 两个自检模式都不出取景画面 —— 跑完就停在那儿，退出要重新烧录。
> 这是刻意的：先把硬件钉死，再谈功能。

### 5. 配网（只做一次）

烧录后设备发现没配过网，会自己开一个热点：

1. 手机搜 WiFi，连上 **`ESP32-CAM-Setup`**（无密码）
2. 一般会自动弹出配网页；没弹就开浏览器访问 **`http://192.168.4.1`**
3. 选一个 WiFi（或手动输 SSID）、填密码，点「保存并重启」

设备重启后连上你的 WiFi，屏幕开始出画面。凭据存在 NVS 里，掉电不丢。

### 6. 日常使用

**开机**：屏幕先闪 红→绿→蓝→白 自检，然后连 WiFi、NTP 对时、出实时画面。
串口每秒打印一次 `[FPS]`。

**板上 BOOT(GPIO0) 键 —— 三个手势：**

| 操作 | 作用 |
|---|---|
| **短按**（松开时不到 1.2 秒）| 拍照认药名 → 本地判断该不该吃 → 结果上屏 + 喇叭读出来 |
| **按住 ≥1.2 秒** | 开始录音（屏幕出电平条），**松手**结束并上传识别 |
| **双击**（两次短按间隔 < 0.4 秒）| 进配网模式，重新配 WiFi |
| **开机时按住不放** | 纯屏幕测试模式（排障用，见下）|

> ⚠️ **配网从"长按 3 秒"改成双击了。** 不改不行：1.2 秒的录音阈值一定先触发，
> 而且「一天两次，早晚各一次」这句话要说 4~8 秒，会把 3 秒阈值撞上、说到一半跳去配网。
>
> 单击拍照会因此多等 **0.4 秒**才开始（要等双击判定窗口关闭）—— 可接受，拍照本身要 5~35 秒。

---

#### 短按：拍照识药

拍照 → 模型只认药名 → **本地**查记忆算时间 → 中文结果上屏 + 喇叭读出来。

> 认出来的药名会**自动记进药品表**（先只有名字，还没有方案）——
> 这样语音那边才认得它（语音要求药名已经在表里）。方案再补一句「一天两次」就行。

屏幕依次显示 `Capturing...` → `Uploading...` → 药名和结论（中文大字）。
串口同步打印：

```
[KEY] 短按 -> 拍照识别药品
========== 模型回答 ==========
阿莫西林
==============================

========== 用药提醒 ==========
阿莫西林: 距上次 08:30 已 3 小时 20 分, 按一天 2 次还不到时间, 再等等。
==============================
```

**只有"认药名"这一步用了模型**，该不该吃全程本地算 —— 不调 API、快、免费，
而且时间算术交给代码比交给模型可靠得多。

**本地判断是两条独立的线，管的是两件事：**

| 线 | 依据 | 管什么 |
|---|---|---|
| **间隔** | 上次服用时间戳 | 两次之间**别太近**（按方案算出该隔多久，取 60% / 80% 两档）|
| **总量** | 24 小时窗口计数 | 一天**别太多** |

⚠️ **间隔够 ≠ 总量够**：一天里均匀地吃 5 次，每一次的间隔都是够的，只有总量拦得住。
所以超量提醒排在间隔判断**前面**。超量时四处都会提醒：语音/屏幕的结论、
记一笔时的回话、网页列表标红、网页点「吃了」之后的结果页。

> 24 小时窗口是**锚定**的（从这一轮第一笔算满 24 小时就归零、开新窗口），
> 不是滚动的 24 小时 —— 跨窗口的两笔不互相计数。要做滚动窗口得存下每笔时间戳，
> 而 NVS 只有 4000 字节，放不下。

#### 按住说话：语音交互

```
按住 BOOT ≥1.2 秒   →  屏幕出 "Recording" + 电平条
说：「阿莫西林吃了」
松开                →  自动上传识别 → 本地判断 → 喇叭读出来
```

屏幕最后停在结果页：`Heard:` 下面是转写原文，再下面是结论。
串口同步打印全过程：

```
[KEY] 按住 -> 录音中, 松手结束并识别
[VOICE] 录到 32000 字节 (1.0 秒), 峰值 6218
[ASR] 请求体 320591 字节 (预期 320591) 一致
[ASR] 转写: 「阿莫西林吃了」
[VOICE] 「阿莫西林吃了」-> 阿莫西林: 已记下这次服用 (08:30), 24 小时内第 1 次。
[TTS] 218400 字节 WAV, 24000 Hz, 1 声道, 音频 4.5 秒
```

**能听懂的几种说法**（药名必须是已经记录过的 —— 拍过照，或在网页上加过）：

| 说法 | 动作 |
|---|---|
| 「阿莫西林**吃了**」/「**服**了」/「喝了」/「滴了」 | 记一次服用（打时间戳 + 24 小时计数 +1）|
| 「阿莫西林**一天两次**」/「每天 2 次」 | 记用药方案 |
| 「阿莫西林」（不带动作词）| 查现在该不该吃 |
| 「阿莫西林**没吃**」/「**忘了**吃」 | **不记**，只回答现在该不该吃 |
| 「阿莫西林能一起吃**吗**？」 | 疑问句也**不记** |
| 「**三天一次**」「一周一次」「早晚各一次」 | 本地算不准，会**拒绝**并请你改说「一天几次」 |

> 顺序是**否定 > 频率歧义 > 方案 > 服用 > 查询**，判断错不会报错、只会安静地把记录写反：
> 比如「没吃」记成"已服用"，接下来还会回你一句「刚吃过，别重复」—— 等于**劝人漏服**。
> 所以宁可少记（你再说一遍就是），也不猜。

> **播报时按一下 BOOT 就能打断** —— 4~8 秒听着不能停会让人烦。

#### 网页

浏览器打开设备 IP（串口和屏幕上都打印了），能做这些：

- 看全部用药记录、上次服用时间、**24 小时内吃了几次**（超量会标红）
- 手动**添加/修改方案**、标记**吃了**、**清空次数**、删除、清空
  - 「清空次数」= 记错了/重复点了一次时用：只把 24 小时的计数归零，
    **上次服用时间和窗口计时都不动** —— 所以它不会让"该不该吃"的判断变松
- **屏幕全白时点一下救命**（`/tftreset`）—— 见下「屏幕纯白」那一节
- **演示助手**（`/demo`）：把记录的时间戳往前挪 6/12/25 小时，
  让"该吃了""24 小时窗口重置"这些本来要等几小时的状态立刻出现 —— 现场演示用，
  改 `webui.h` 的 `DEMO_HELPERS` 可以关掉
- **打字代替说话** —— 输入「阿莫西林吃了」走的是和语音**完全相同**的处理链路
  （同一个 `medHandleUtterance()`），结果同样会用喇叭读出来。麦克风没接/坏了时靠它兜底
- **看最近拍的那张照片**（`/photo`）—— 调识别精度时能亲眼看到模型收到的是什么
- 看最近一次语音的转写原文和答复

> 拍照期间取景会**停住**（摄像头切模式 1~2 秒 + 上传等模型 5~35 秒，全程不取景），
> 之后自动恢复。期间屏幕停在状态文字上，别以为死机了。
>
> 语音交互全程也**不取景**（录音 + 上传 + 播报加起来约 20~60 秒）—— 屏幕归语音用，
> 这时候看电平条和状态文字就行。**但网页照常能打开**，结果照样能看。

**想改问法 / 模型 / 分辨率**，看 `src/vision.cpp` 顶部：
`ASK_PROMPT`（提问词）、`ZHIPU_MODEL`（模型 ID）、`SHOT_FRAMESIZE`（拍照分辨率）。

**想改语音参数**，看 `src/voice.h` 顶部：采样率、录音时长上限、静音阈值都在那儿（**引脚在 `src/pins.h`**）。

## 拍照为什么要切摄像头模式

拍照时取景会中断，因为摄像头要从 **RGB565 / QQVGA 160x120**（取景）切到
**RGB565 / SVGA 800x600**（拍照），拍完再切回来。切模式本身约 1~2 秒，
加上等模型的时间，整个拍照流程期间都不取景（共约 5~35 秒）。

这个切换**必须** `deinit` + 重新 `init`，不能用 `set_pixformat()` / `set_framesize()` 热切换：

- framebuffer 是 `esp_camera_init()` 时按模式算好分配的（`cam_config()` 只被它调用）
- 运行时的 `set_pixformat()` / `set_framesize()` **只改传感器寄存器**，不碰 ESP32 侧的帧缓冲几何
- 尺寸一变就是 **DMA 越界写 PSRAM** —— 不是画质变差，是内存破坏

> TLS 握手要 40~50KB **连续**内部内存。真遇上「TLS 连接失败」，
> 把 `main.cpp` 的 `static uint16_t viewBuf[...]` 改成
> `static uint16_t *viewBuf;` + 启动时 `heap_caps_malloc(VIEW_W*VIEW_H*2, MALLOC_CAP_SPIRAM)`，
> 就能腾出 38KB 内部 RAM（用法不用改，`viewBuf[i]` 照样能写）。
> 代价是取景时每帧多几次 PSRAM 写入。

## 为什么不用硬件 JPEG

OV3660 自带 JPEG 编码器，本来该直接出 JPEG。但 **esp32-camera 的 ov3660 驱动里，
`ov3660_settings.h` 的 `sensor_fmt_jpeg[]` 写的其实是 YUV422/YUYV 的配置**
（连驱动自己的注释都这么标），调用 `set_pixformat(PIXFORMAT_JPEG)` 时传感器
**根本没切进 JPEG 模式**；而 ESP32 这边 `cam_config()` 是按 JPEG 工作的（在数据流里
找 SOI/EOI 标记），于是永远攒不出一帧。

实测表现很干脆：**JPEG QVGA / VGA / SVGA 全部 8 秒超时零帧，而 RGB565 连 VGA 都能
稳定拿到 614400 字节的完整帧**（格式不对，跟分辨率无关）。

所以固件改成**拍 RGB565，再用 `frame2jpg_cb()` 软件编码成 JPEG**。这样反而更省内存：
带回调的版本可以把输出直接写进 PSRAM，而不带回调的 `frame2jpg()` 内部是裸 `malloc`
（内部 RAM），VGA 下要 60~120KB，会把堆打碎、连累紧随其后的 TLS 握手。

代价是编码耗时（VGA 约 200~400ms），相比整个 5~35 秒的流程可以忽略。

## 语音部分详解

### 硬件：为什么两个模块共用时钟

INMP441（麦克风）和 MAX98357A（功放）**共用 BCLK(GPIO41) 和 WS(GPIO42)** 两根线，
靠分时切换 I2S 方向来区分：

| | 录音 | 播报 |
|---|---|---|
| I2S 模式 | MASTER + RX | MASTER + TX |
| 采样率 | 16000 Hz | 24000 Hz（GLM-TTS 固定输出这个）|
| 数据脚 | GPIO40 → INMP441 SD | GPIO39 → MAX98357A DIN |
| 声道格式 | `ONLY_LEFT` | `RIGHT_LEFT` + 手动展开成 L/R |

**为什么不给两个模块各配一组时钟**：ESP32-S3 上非 strapping 的空闲脚只有
`38/39/40/41/42` 五个，两组独立 I2S 各要 3 根线，凑不齐；而且录音和播报本来就
不同时发生。

**为什么功放的 SD 要走 GPIO38**：录音时 BCLK/WS 一直在翻转（主模式要产生时钟），
而 DIN 此刻是悬空的 —— MAX98357A 看到时钟就工作，会把悬空脚的噪声放大出来，
再被麦克风录回去（自激）。所以使能脚必须能被软件关掉，只有播报时才拉高。

**为什么播报要把单声道展开成立体声**：MAX98357A 在 SD 拉高时工作在 `(L+R)/2` 模式。
只往左声道发数据、右声道恒为 0 的话，混音后**音量直接减半** ——
症状是"能响但明显偏小"，很容易误判成功放模块或供电的问题。

### 录音链路

```
按住 BOOT ≥1.2 秒
   ↓ mic_task 被唤醒（core 1，优先级 3）
I2S RX @16kHz/16bit → PSRAM 缓冲，每 64ms 更新一次电平条
   ↓ task 自己高频轮询 GPIO 检测松手
松开 → 停止 → 填 64 字节 WAV 头
   ↓ multipart/form-data，用 file 分片（不用 base64，省 427KB 缓冲）
POST /api/paas/v4/audio/transcriptions  (glm-asr-2512)
   ↓ 转写文字在响应的【顶层 text 字段】
medHandleUtterance() —— 纯本地判断
   ↓
GLM-TTS → WAV 字节 → MAX98357A 播放
```

**为什么录音要独立 task**：主循环的按键检测只有 ~17Hz，而且拍照/上传会让
`loop()` 干脆阻塞几秒 —— 靠主循环采样根本抓不住松手时刻，只会一路录到 10 秒上限。
task 用 `i2s_read` 的间隙高频轮询 GPIO，才抓得准。

**为什么缓冲要开机一次性分配**：摄像头的 `deinit`/`init` 反复申请释放 960KB
framebuffer，PSRAM 本来就贴着碎片化边缘。录音缓冲 320KB + **播放缓冲 2MB**
在 `voiceBegin()` 里一次分配、长期持有，不反复申请释放。

（播放缓冲给到 2MB 是**实测**的结果：一句话的 TTS 音频能把 512KB 撑满还不够。
早先判断是"返回了立体声"，**后来查明不是** —— WAV 头写着 `24000 Hz, 1 声道, 16 bit`，
11.6 秒 × 24000 × 2 字节 = 556,800，和实测的 558,480 对得上，就是单声道。
当年是**把时长估错了**：TTS 念的文本比预想的长（还要加免责声明那一句）。
所以缓冲要按 **48KB/s（24kHz 单声道）** 估，一句话十几秒就是半 MB 起步。）

**为什么 PCM 从偏移 64 开始而不是 44**：ESP32-S3 的 GDMA 访问 PSRAM 要求 16 字节对齐，
44 不是 16 的倍数。做法是在 WAV 的 fmt 和 data 之间塞一个 20 字节的 `JUNK` 对齐块
（RIFF 里合法存在的填充块），让 `data` 如实落在 56、PCM 落在 64。

### 静音检测：先排除接线，再谈识别

录完先判断，**不通过就不调 API** —— 省一次调用，更重要的是别让人误以为是
"识别不准"而去调 prompt：

| 判定 | 条件 | 屏幕上会出现 |
|---|---|---|
| **数据线死了** | 整段一个值都不跳，或 99% 以上是 0 | 「麦克风没有输出。检查接线…」|
| **没听到声音** | 峰值 < 200（16bit 满量程 32768）| 「没听到声音，请靠近麦克风…」|

这两条挡的是**接线问题**，不是识别质量问题。INMP441 没接好的典型症状就是
「一切正常但全是 0」—— 没有这道拦截会白白浪费一次 API 调用，而且查不到方向。

### 播报文本做了两件事

1. **截断**到 100 字。按字符计费，而且提醒本来就该短。截断时往前退到完整汉字，
   免得截出半个 UTF-8 字符变成乱码
2. **加免责**：「以上仅供参考，请以医嘱和说明书为准。」——
   药品场景的安全边界：输出要是"陈述 + 免责"，不是"指令"

### 关于热词（hotwords）

ASR 请求带了一个 `hotwords` 表来提高药名的识别率，内容是：

**设备里已经记录过的药名**（排最前面 —— 用户会说的基本就是这些）
**+ 内置的常见药名**（阿莫西林、布洛芬、氯雷他定…，见 `med.cpp` 的 `kCommonDrugs`）

> 早先这里刻意**不用**用户自己的药单，理由是"别把健康信息随每次请求发给智谱"。
> 那个理由其实不成立：药名早就通过三条路进智谱了 —— 药盒照片（glm-4.6v）、
> 播报文本（GLM-TTS）、以及**用户嘴上说的那一句，就在同一个 ASR 请求的音频里**。
> 而药名恰恰是热词最该起作用的地方。

⚠️ **实测存疑**：说「苯磺酸氨氯地平片」被转写成「酸氯环利晴片」，
而内置表里**本来就有「氨氯地平」** —— 所以热词要么被服务端静默忽略了，要么力度不够。
接口文档说 `hotwords` 是字符串数组、上限 100 个，格式对得上，所以"格式错"解释不了它。

留了个三档开关 `ASR_HOTWORDS_FMT`（`src/voice.cpp` 顶部）用来做对照实验：

| 值 | 发出的内容 | 用途 |
|---|---|---|
| `0` | **不发 hotwords 字段** | 对照档：同一句话录两遍，转写一字不差 = 服务端没理这个参数 |
| `1` | JSON 数组 `["阿莫西林",…]` | 默认（和接口文档一致）|
| `2` | 逗号分隔 `阿莫西林,…` | 社区工具的写法 |

每次录音串口都会把**实际发出去的热词原样打出来**，不用猜。

### 语音排障

| 现象 | 查这里 |
|---|---|
| **设备不重启但完全没反应**（连 `[FPS]` 都不打）| 语音 task 卡住了 —— 它一卡 `voiceBusy()` 就永远为真，主循环每帧直接 `return`，看着像死机。看串口**最后停在哪一行** |
| 串口停在 `chunked 解出 N 字节` | N 正好等于缓冲大小 = **音频超出了播放缓冲**。调大 `voice.cpp` 的 `TTS_BUF_BYTES`（当前 2MB）|
| **读数恒定（全 `0x0000` 或 全 `0xFFFF`）** | ⚠️ **第一件事是把每根线重插一遍** —— 接触不良和"麦克风烧了"的症状**完全一样**，光看数值分不出来。用 `HW_TEST` 看 `全0/全FF/其他` 三列 |
| 按住没反应，串口也没打印 | 按住时间不够 1.2 秒；或上一段语音还在处理（串口会打「上一段还没处理完」）|
| 屏幕显示 `Mic DEAD` | 麦克风数据线没输出。查 L/R 是否接 GND、VDD 是否 3V3、SD 是否 GPIO40 |
| 屏幕显示 `No sound` | 有信号但太弱。靠近点说，或调 `voice.h` 的 `VOICE_SILENT_PEAK`（默认 200）|
| 电平条一直满格 / 有持续底噪 | **功放自激**：SD 是不是直接接了 3V3 而没走 GPIO38 |
| 电平条完全不动 | 麦克风侧没通，见上面两行 |
| 转写出来是空的 | 串口会打原始响应。多半是取错字段（`text` vs `content`），或 hotwords 格式被拒 |
| `[ASR] HTTP 400` | 看串口打的响应体。多半是 hotwords 格式 → 切 `ASR_HOTWORDS_FMT`（见「关于热词」） |
| `[ASR] 请求体 N 字节（预期 M）!! 不一致` | multipart 拼装坏了。**差 1 字节服务端就挂起或回 400**，很难查，所以专门打了这行 |
| 播报没声音，但串口显示 TTS 成功 | 功放侧：VIN 是不是 5V、SD(GPIO38) 有没有接对、SPK± 是否接在喇叭两端 |
| 播报声音明显偏小 | 单声道没展开成立体声（见上文），或 GAIN 脚被接了 |
| **播放开头有"嘟嘟"/摩斯电码声** | DMA 环形缓冲里的**随机内存**被放出来了。要先灌满静音再开功放（`voice.cpp` 的 `playWavBuffer()`，注释里写了三个成因）|
| `[写] 首次受阻` / `请求体写到一半断了` | **上传分块太大** —— 这台设备 mbedtls 出方向大 TLS 记录会被对端掐死，必须 64 字节一块（`ASR_UPLOAD_CHUNK` / `uploadChunkGuess`），别改大 |
| 播报音调怪 / 时长翻倍 | TX 采样率和 WAV 头里的对不上。看串口的 `[TTS] … Hz` 那行 |
| 识别不准 | 说慢一点、靠近麦克风。热词表自动带「已入库的药名」—— 先确认这味药拍照入过库 |
| 播报念错字 | GLM-TTS 的问题，换个 `TTS_VOICE`（彤彤 / 小陈 / jam 等）试试 |

## 配网细节

- **自动进配网**：没配过网，或者开机 10 秒内连不上路由器
- **手动进配网**：运行中**双击 BOOT**（两次短按间隔 < 0.4 秒）
- **自动退出**：5 分钟没人操作会重启（回到取景模式，但 WiFi 仍未连接）
- 配网页面是 ESP32 自己开热点提供的，**整个过程不需要外网**
- 热点名和超时时间在 `src/netcfg.cpp` 顶部 `AP_SSID` / `SETUP_TIMEOUT`

> 密码填错了也不怕：重启后连不上，会**自动重新回到配网模式**，不会变砖。

> 配网是在**第二击松开的那一刻**触发的（不是按下时）—— 所以不会出现
> 「手还按着就重启、重启后 GPIO0 仍是低电平被当成开机测试模式」那种情况。

### OV3660 画面方向

OV3660 出厂默认输出的画面是**上下颠倒**的，由传感器默认寄存器 `0x3820=0x40` / `0x3821=0x00` 决定，**不是接线问题，也不是 `TFT_ROTATION` 没调对**。

> ⚠️ 2026-10-06 修正：早先这里写的是「上下颠倒 **+ 左右镜像**（转了 180°）」，**那个前提是错的** ——
> 实测只有上下颠倒，**没有左右镜像**。当初按 180° 去补，反而给两条路都多转了半圈，
> 于是**取景和拍照双双变成左右镜像**（字左右反着、上下正常）。因为两条路一起错，
> 屏幕上看着自洽，只有把照片和实物并排比才能发现。

修法是在 `buildView()` 降采样时**反向取行号**，由 `CAM_VFLIP` 控制（拍照那条路是 `vision.cpp` 的 `SHOT_VFLIP`）：

| 屏幕上看到 | `CAM_VFLIP` |
|---|---|
| 倒过来（OV3660 出厂就是这个）| 1 |
| 本来就是正的 | 0 |

只是换了索引顺序，取的仍是同一批像素，所以**零开销、不影响颜色、也不影响屏幕 UI 文字方向**。

⚠️ **两条路必须用同一种变换。** `buildView()`（取景）和 `shotAndAsk()`（拍照）读的是同一份 `fb->buf`，
任何一边的补偿方式跟另一边不一致，就会出现「屏幕正、照片反」；而两边**都错**反而看着一致，更难发现。

> ⚠️ **不要在传感器端翻**（别去调驱动的镜像/翻转接口）。它的底层 `set_image_options()` 会连带重写
> `0x4514` / `0x4520` / `X_INCREMENT` / `Y_INCREMENT`，在 OV3660 + RGB565 下会把画面搞成
> **斜切（平行四边形）+ 颜色错乱**。
>
> 也不要自己去写 `0x3820`/`0x3821`：翻转会改变 Bayer 顺序，必须靠 `0x4514` 一起补偿，漏了就是红蓝互换。

**排查这类问题的固定动作**：打开 `SHOT_PREVIEW` → 对着有字的药盒 → **同时**看屏幕取景和网页 `/photo`，
两个都跟实物比。别靠推理。

## 屏幕纯白 / 花屏 怎么修（固件已内置排障）

**先分清是"开机就白"还是"用着用着突然白"—— 两个完全不同的原因。**

### A. 用着好好的，手一碰杜邦线就全白（线上最常见的故障）

线**根本没断开**，就是手碰了一下。原因是 80MHz 时 SPI 的位周期只有 12.5ns，
杜邦线不是传输线，手一动寄生电容就变、边沿振铃多采一个时钟 = 某位翻掉；
而屏幕初始化时连发的三条命令里**有两条与「关显示」只差一位**
（`CASET(0x2A)` 翻一位 = `0x28` DISPOFF、`RAMWR(0x2C)` 翻一位也是 `0x28`），
面板一旦收到就关掉显示 —— 而固件里除了开机那张初始化表，**再没有第二条"DISPON"**，
所以白到重启。

**已经防住了三件事**：

1. **每帧补一条 DISPON** —— 再碰线最坏只是闪一帧（约 56ms）
2. **SPI 从 80MHz 降到 27MHz** —— 远离杜邦线的谐振点（实测帧率一点没掉）
3. **网页上「屏幕全白? 点这里重置屏幕」**（`/tftreset`）—— 万一真被抖成软复位，
   手机点一下重跑初始化，不用跑到设备跟前拔电

> **根因还是那根线**：把线固定住（胶带/热熔胶）或焊上，比什么补救都强。

### B. 开机就一直纯白

开机固件会依次闪 红→绿→蓝→白 自检，然后才开摄像头：

- **闪了** → 屏幕和接线没问题，问题在画面数据（改 `CAM_MSB_FIRST` / `SPI_SPEED_HZ`）
- **一直纯白，一点变化都没有** → 屏幕侧没通，按下面顺序查：

1. 按住板上 **BOOT(GPIO0)** 再复位 → 进入纯屏幕测试模式（循环红/绿/蓝/白/彩条/棋盘+文字框），排除摄像头干扰
2. **核对 6 根线是不是接在 IO21 / IO14 / IO47 / IO48 / IO1 / IO2** 上。
   想换脚就改 **`src/pins.h`**（全项目引脚都在那一个文件里）。
   ⚠️ 但空脚真的不多了：**摄像头占 4-18、I2S 占 38-42、Flash+八线 PSRAM 占 26-37**，
   剩下没被占的只有 3/45/46，而它们**全是 strapping 脚**
3. 检查 RES/DC/CS 有没有接错位（这三根接错=纯白），DC 必须接 IO48、CS 必须接 IO47
4. 模块 VCC 先试 **5V**（很多 1.8" ST7735S 模块板载 3.3V LDO，3.3V 供电时控制器电压不够，背光亮但不出图）
5. 排线尽量短、别用劣质杜邦线；初始化速度已降到 8MHz

tab 变体（面板初始化方式）**默认已锁定 `INITR_BLACKTAB`**（`TFT_TAB_AUTO` 为 0）。

`TFT_TAB_AUTO` 曾经默认为 1，那样**每次复位都会换一个 tab**，画面会在「正常」和「斜切/偏移 + 颜色错乱」之间来回跳，看起来像是硬件坏了、其实只是 tab 变了，极难排查。如果你动过这部分配置，务必确认它已经关掉。要试别的 tab，直接改 `TFT_TAB` 为 `INITR_GREENTAB` / `INITR_REDTAB`。颜色变反色（像底片）就把 `TFT_INVERT` 改成 1。

## 性能

- 采集：**QQVGA 160x120 RGB565**，双缓冲 + `CAMERA_GRAB_LATEST`，永远拿最新帧
- **为什么必须是 QQVGA**：OV3660 驱动给不同尺寸分配了两档 PLL，帧率差近一倍 ——
  QVGA 及以上 10.25 FPS，低于 QVGA 才切到 **17.77 FPS**
- 处理：QQVGA 正好等于屏幕的 160x120，1:1 直出，`buildView()` 走快速路径（只搬字节 + 换序），单帧 < 1ms
- 传输：SPI **27MHz** 发 38400 字节 ≈ 11.4ms
- **实测 17FPS** —— 帧周期由**传感器**决定（约 56ms），SPI 那十几毫秒躲在"等下一帧"的空档里。

> ⚠️ 所以**降 SPI 速度不会掉帧**：从 80MHz 一路降到 27MHz，实测帧率始终是 17FPS。
> 当初担心"降速会掉 2 帧"是估错了。反过来，想提帧率也别在 SPI 上使劲 ——
> 瓶颈在传感器那一档（见上面 QQVGA 的说明）。

> 拍照不受这套参数影响：取景用 QQVGA 图快，拍照会切到清晰的那一档。

帧率上不去时按这个顺序查：① `VIEW_FRAMESIZE` 是不是被改回了 QVGA（那会掉到 10FPS 档）；
② 是不是刚按过拍照 —— 那段是阻塞的，拍照和上传期间不取景。

### 语音对性能的影响

**取景会暂停，而不是变慢。** 录音/上传/播报期间主循环直接跳过取景，帧率是 0 ——
这是刻意的：省下的 CPU 和 PSRAM 带宽留给 I2S 和 TLS，也避免 TFT 刷屏和 I2S 抢 core 1。
播报完自动恢复。

| 阶段 | 耗时 | 取景 |
|---|---|---|
| 录音 | 按多久录多久（上限 `VOICE_MAX_SEC`）| 停，屏幕显示电平条 |
| ASR 上传 | 5~30 秒 | 停，屏幕显示 `ASR upload...` |
| TTS 合成 + 播报 | 3~10 秒 | 停，屏幕显示 `Speaking...`（可按 BOOT 打断）|

**但这几段时间里网页照常能用** —— `webuiLoop()` 没有被跳过，所以结果能立刻在手机上看到。
这也是播报走异步的原因：同步播的话网页会跟着停摆，而结论恰恰要显示在网页上。

**内存**：语音额外占约 **2.4MB PSRAM**（320KB 录音缓冲 + 2MB 播放缓冲，开机一次性分配）
和约 17KB 内部 RAM（主要是 12KB 的语音 task 栈）。8MB 的 PSRAM 完全放得下。

> 语音 task 跑在 **core 1**、优先级 3（高于 `loopTask` 的 1，远低于 WiFi 的 ~23），
> core 0 留给摄像头的 `cam_task` 和 lwIP。
